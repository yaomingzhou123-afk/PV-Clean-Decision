# PV-Clean-Decision · 评委问答参考回答

**说明：以下所有回答均以当前代码为准，不含虚构内容。测试数据来自实际运行，非编造。**

---

## 一、项目选题

**Q1：为什么选择光伏清洗决策这个方向？**

> 新疆是光伏大省也是沙尘频发区，组件积灰导致发电损失最高可达 15%（模型上限）。但 20MW 电站一次全站清洗约 4,000 元（人工+用水+设备），盲目清洗浪费资源。核心问题是清洗收益、清洗成本、作业安全三重约束下的最优决策，目前主要依赖人工经验，缺乏可解释、可追溯的量化工具。这个方向有明确的场景价值和量化空间。

**Q2：这个项目的核心价值是什么？**

> 四个字：可解释。传统清洗决策是"师傅觉得该洗了"，我们的系统输出的是"因为 PM10 135 微克、无雨 20 天、估算污损 15%、净收益 39,478 元、回本 1.2 天，所以建议清洗"——每一步都有公式、参数来源和证据表。同时 Safety 可否决、Critic 可驳回、数据不足拒绝决策，不是黑盒。

---

## 二、多 Agent 必要性

**Q3：为什么需要七个 Agent？一个规则引擎不够吗？**

> 一个规则引擎能算净收益，但做不到三件事：第一，Safety 需要独立于经济计算的否决权——不能因为赚钱就忽略风速超限；第二，Critic 需要独立于计算方的审查权——不能因为算出了数字就不复核；第三，每个 Agent 输出的是结构化证据（结论+证据表+数据源+假设+不确定性），便于追溯和解释。七个 Agent 不是为凑数量，是分工+制衡。

**Q4：七个 Agent 是怎么协作的？**

> 顺序执行：气象→污损→发电→经济→安全→审查→决策。所有 Agent 读取同一份 metrics/config 输入快照，关键数学计算全部来自 pv_model 确定性模块，Agent 只做分析、解释、审查和裁决，不自行产生数值。Safety 发现超限输出 veto，Critic 发现问题输出 reject，Decision Agent 按保守序（clean < hold < defer < insufficient_data）仲裁，最终决策不会比规则更激进。

**Q5：Agent 之间数据怎么传递？**

> 统一输入：所有 Agent 读取同一份 `metrics`（由 pv_model.compute_metrics 计算）和 `config`（电站配置）。统一输出：每个 Agent 输出 AgentResult 结构（agent_name/status/conclusion/evidence/data_sources/assumptions/uncertainties/recommendation/confidence_type/confidence），并通过 `_validate_result` 结构校验——缺字段或类型错误标记为 error 不进入决策。

---

## 三、积灰判断

**Q6：积灰模型怎么算？依据是什么？**

> 线性累积模型：日污损速率 = 基础速率(0.4%/天) + max(0, PM10−80) × 0.00035 + max(0, PM2.5−35) × 0.00005（演示系数）；污损损失率 = min(15% 上限, 日速率 × 天数 × 倾角因子)。依据：基础速率和 PM10 系数来自公开研究趋势标定（IEA PVPS 文献），待实测修正；所有输出标注 method=model_estimate，明确不是传感器实测。

**Q7：你们怎么验证积灰模型的准确性？**

> 坦诚说：没有实测验证。我们没有接入真实电站的积灰传感器数据，模型是文献区间的保守值。但我们做了三件事：第一，敏感性分析 12 场景，改变污损速率 ±20% 看决策是否翻转；第二，模拟实验室允许手动覆盖污损值观察结果；第三，代码和文档明确标注 model_estimate 和模型限制。准确性需要后续用实测数据校准——这是当前最大的局限。

**Q8：为什么用 PM10 而不是直接测组件积灰？**

> 因为公开数据源只有 PM10/沙尘预报，没有组件级积灰传感器数据。PM10 是沙尘浓度的代理变量，趋势正确但精度有限。我们明确标注了局限：线性累积假设、未建模沙尘事件突发性、未建模组件类型差异。落地时需要接入实测发电量或积灰传感器校准。

---

## 四、PM10/PM2.5 局限

**Q9：PM2.5 在模型里起什么作用？**

> 在模拟实验室里，PM2.5 高于演示基准 35 时按演示系数 0.00005 增加日污损速率。这个系数没有实测依据，纯演示用途，界面和文档都标注了"演示假设，不代表行业标准"。主决策链路（demo/live）默认不启用 PM2.5 系数（pm25_factor=0），保持与文献口径一致。

**Q10：如果 PM10 数据源失败怎么办？**

> PM10 缺失时系统输出 insufficient_data，不会用默认值编造污损损失。`_check_data_sufficiency` 检查 PM10 是否 None，缺失即数据不足。demo 模式用内置样例 PM10=135，标注 is_simulated=true。

---

## 五、数据真实性

**Q11：你们的数据是真的吗？**

> 分三类。天气和空气质量：Open-Meteo 免费 API，真实接口，失败自动降级为内置样例并标注 is_simulated=true。理论发电量：PVGIS（欧盟 JRC，ERA5 2005-2023 历史气候均值），真实接口，标注 data_kind=historical（非实时）。污损/收益：模型估算，标注 method=model_estimate。每条数据有 9 个元数据字段，前端数据质量面板逐条展示。

**Q12：怎么证明你们没有用模拟数据冒充真实数据？**

> 三个机制。第一，数据质量面板逐条展示 is_simulated、status、error_message，模拟数据金色标注"模拟"。第二，live 模式下关键源（预报/空气质量）降级为 fallback 时，系统直接输出 insufficient_data——不用模拟数据给真实决策。第三，Critic 规则审查包含"模拟数据误标"检测：如果 Agent 声称基于实时数据但数据源是 simulation，Critic 会报高危问题。

## 六、现场传感器缺失

**Q13：没有积灰传感器，污损率怎么保证可信？**

> 不保证。我们明确说污损率是模型估算（method=model_estimate），不是实测。可信度的来源是：参数来源可追溯（文献区间保守值）、敏感性分析可复现、模拟实验室可现场调参验证、落地后可接实测数据校准。比赛阶段我们诚实标注局限，而不是虚构一个"95% 准确率"。

**Q14：如果接入实测数据，系统需要改什么？**

> 只需要替换 `weather.py` 的数据源调用。把 PM10 从 Open-Meteo Air Quality 换成电站实测的积灰传感器/无人机巡检数据，把 PVGIS 均值换成实测发电量。`pv_model` 的计算逻辑不变，`agent_team` 的分析逻辑不变，前端展示不变。接口契约是 `forecast/air/theoretical` 三个字段，数据源换实现就行。

## 七、经济性计算

**Q15：净收益公式具体怎么算？**

> 有效可恢复损失 = 污损损失率 × 恢复效率(0.95) × (1 − 自然清洁折减)。日增量收益 = 理论日发电量 × 有效损失 × 1000 × 电价。净收益 = 日增量收益 × 评估周期(14 天) − 清洗成本 − 停机损失。停机损失 = 理论日发电量 ÷ 24 × 停机小时(4h) × 电价 × 1000。所有参数有来源标注，电价是新疆燃煤标杆政策值，清洗成本是公开招标区间。

**Q16：分区清洗的恢复效率怎么算的？**

> `apply_partial` 中 `recover_ratio = ratio + 0.10`，即分区清洗后恢复效率略高于平均（优先清洗高污损区域）。这是一个保守假设，没有实测依据，文档已标注。分区比例按污损损失率/上限归一化在 30%–70% 之间线性映射。答辩时应说明这是模型假设，落地后需实测校准。

---

## 八、Safety 否决机制

**Q17：Safety 什么时候否决？**

> 三条件否决，优先级从高到低：① 数据质量否决——live 模式下关键数据源含模拟记录；② 天气否决——未来 48 小时降水 ≥ 1mm 或风速 ≥ 12 m/s（用户配置阈值）；③ 间隔否决——距上次清洗 < 14 天（最小清洗间隔）。否决后 Decision Agent 必须遵守保守序：data_quality→insufficient_data，weather→defer，interval→hold。

**Q18：如果 Safety 否决了但经济上应该清洗，怎么办？**

> Safety 否决优先于经济收益。这是设计原则：不能因为净收益高就忽略风速超限（高空作业风险）或数据不足（决策不可信）。代码里 `_CONSERVATIVE_RANK = {"clean": 0, "hold": 1, "defer": 2, "insufficient_data": 3}`，Decision Agent 取保守序更高的那个。

---

## 九、Critic 否决机制

**Q19：Critic 怎么审查？**

> 四类确定性规则审查：① 计算复核——净收益 = 收益 − 成本 − 停机，容差 2 元；② 结论矛盾——Safety 天气否决时 Weather 仍判窗口适合；③ 模拟数据误标——数据源含 simulation 但 Agent 声称基于实时数据；④ 单位抽查——降雨应为 mm、风速 m/s、污损 %、净收益 元。发现高危问题输出 reject，Decision Agent 收到 reject 后阻止 clean 决策。

**Q20：Critic 的 LLM 增强是什么？**

> Critic 支持将七 Agent 结论交 LLM 补充审查（限 1 次调用，温度 0.1），输出必须通过 JSON 结构校验（`{"issues": [{agent, issue, severity}]}`），不合规返回 None 跳过。LLM 不可用时规则审查独立完成。这是可选增强，不是依赖——演示时断网/无 Key 也不影响决策。

## 十、模型错误处理

**Q21：如果模型算错了怎么办？**

> 三层防护。第一，Critic 计算复核：净收益公式容差 2 元内复核，不一致报高危 reject，Decision 阻止清洗。第二，结构校验：每个 Agent 输出必须通过 `_validate_result`，缺字段/类型错误标记 error 不进入决策。第三，参数校验：Pydantic 422 拦截非法输入，超出范围直接报错。没有任何一层是"相信模型不会错"。

**Q22：MCP 调用失败怎么办？**

> MCP 子进程有 30 秒读超时（队列+读线程实现，Windows/Linux 跨平台兼容），握手失败自动回退进程内直连，不中断主决策。每个工具调用有 elapsed_ms 记录。MCP 是工具层增强，不是依赖——demo 模式、断网、MCP 失败都能跑完决策。

## 十一、竞品区别

**Q23：跟现有的光伏运维系统比有什么区别？**

> 现有系统侧重监控和告警（发电量降了就告诉你），我们的核心是**决策**——要不要洗、什么时候洗、值不值。差异点：① 多 Agent 治理链（否决+审查+仲裁），不是单一规则；② 经济性量化（净收益、回本周期、敏感性分析）；③ 数据可信标注（每条数据标注来源和是否模拟）；④ 模拟实验室（评委现场调参验证策略）。

---

## 十二、创新点

**Q24：最大的创新点是什么？**

> 全链路数据可信标注 + 双否决治理链。不是堆功能，而是保证每个结论有据可依：数据不足拒绝决策、模拟数据标注模拟、Critic 发现计算错误阻止清洗、Safety 风速超限一票否决。这在学生项目中很少见——大部分项目的创新是"加了一个功能"，我们的创新是"加了一层治理"。

**Q25：有没有用到 LLM？LLM 的作用是什么？**

> LLM 是可选增强层，不是主决策依赖。两个用途：① Critic 审查增强——把七 Agent 结论交 LLM 补充审查，输出必须过结构校验；② Function Calling 问答——自然语言提问时 LLM 自主调用 MCP 工具获取数据并回答。LLM 不可用时全部降级为规则引擎，演示零风险。

## 十三、项目不足

**Q26：这个项目最大的不足是什么？**

> 三个坦诚的不足。第一，污损模型没有实测校准——用的是文献区间保守值，准确性待验证。第二，PM2.5 演示系数、倾角映射、分区恢复效率都是假设，没有实测依据。第三，目前未接入真实电站数据，未产生真实收益。我们把这些写在文档里，而不是藏起来。

**Q27：如果评委质疑测试数据是编的，怎么办？**

> 现场跑一遍。测试命令是 `python3 -m pytest backend/tests -q`，206 项全部通过，用时约 30 秒。每一项测试都是可执行的代码，不是截图或文档声明。稳定性修复的 28 项回归测试覆盖了所有 P0 场景，可以当场指定一个场景让评委看测试跑。

## 十四、落地路径

**Q28：这个系统怎么落地到真实电站？**

> 四步：第一步，接入电站 SCADA 实测发电量，替换 PVGIS 均值口径，校准污损模型参数；第二步，接入现场积灰传感器或无人机巡检数据，替换 PM10 代理估算；第三步，对接实际清洗工单与合同价格，替换示例成本假设；第四步，部署至电站运维平台，按方阵粒度输出分区清洗计划。每步只需替换数据源或配置，决策逻辑不变。

## 十五、测试与工程

**Q29：206 项测试都是什么？有没有水分？**

> 没有水分。覆盖七类：决策模型 46 项（公式、边界、四种决策、敏感性、PM2.5、override）、七 Agent 22 项（执行顺序、结构校验、Safety 否决、Critic 检测/误报消除）、稳定性修复回归 28 项（P0 全量 10 项）、MCP 协议 19 项（工具定义、参数校验、超时、泄漏）、模拟实验室 30 项（17 参数重算、负收益不清洗、安全不清洗、非法输入）、REST API 31 项、数据源/RAG 30 项。没有一项被删除、跳过或降低断言。

**Q30：MCP 有必要吗？直接调 HTTP 不行吗？**

> MCP 的价值是标准化工具协议。直接调 HTTP 也能拿到数据，但 MCP 提供了：JSON-RPC 2.0 统一协议、参数校验（-32602）、工具自描述（tools/list）、失败降级、读超时。这在多工具、多 Agent 场景下比每个接口单独封装更可维护。演示时可以展示 MCP 握手和工具调用过程，证明不是包装层。

## 十六、补充问题

**Q31：RAG 知识库有多少条？来源可靠吗？**

> 36 条，覆盖风速安全、清洗窗口、污损速率、清洗成本、分区清洗、最小间隔等主题。23 条已核实（verified=true），来源包括 IEA PVPS 报告、公开招标区间、行业标准。未核实条目标注 source 为"团队经验/待核实"，不伪装为权威。RAG 用 BM25 检索，为 Agent 提供领域知识上下文。

**Q32：Windows 上能跑吗？**

> 能。第七阶段修复了 MCP 的 Windows 兼容问题（select 不支持管道 → 改用队列+读线程），177 项 MCP 测试在 Windows 和 Linux 都通过。一键启动：Windows 双击 run.bat，Linux/macOS 执行 bash run.sh。
